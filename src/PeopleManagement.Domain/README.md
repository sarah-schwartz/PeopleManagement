# PeopleManagement.Domain

## Purpose

The innermost layer of the solution. It defines the `Person` entity — the single aggregate that models a real person in the system — with no dependency on any framework, database, or HTTP library.

## What it contains

| File | Role |
|------|------|
| `People/Person.cs` | The `Person` aggregate root |

### Person entity

```
Person
├── Id              (int, auto-generated by the database)
├── FullName        (string, max 200 chars)
├── Email           (string, max 320 chars)
├── Phone           (string, max 20 chars, optional)
├── ProfilePhotoStoredPath (string, max 512 chars, nullable)
├── CreatedAtUtc    (datetime2)
└── UpdatedAtUtc    (datetime2)
```

Properties are private-set. The entity exposes `internal` methods (`StampAsCreated`, `StampAsModified`, `SetProfilePhotoStoredPath`) that only `PeopleManagement.Infrastructure` may call, enforced via the `[assembly: InternalsVisibleTo("PeopleManagement.Infrastructure")]` attribute in the `.csproj`.

All field-length constants (`FullNameMaxLength`, `EmailMaxLength`, etc.) live on the entity and are reused by the EF Core configuration and FluentValidation rules — a single source of truth for constraints.

## Why this implementation is appropriate

- **Zero external dependencies** — the project has no NuGet packages. This means the domain logic can be tested, reasoned about, or reused in any .NET context without pulling in infrastructure concerns.
- **Constants on the entity** — placing `FullNameMaxLength = 200` directly on `Person` removes the risk of the database column and the validator drifting out of sync.
- **Private setters** — properties cannot be modified arbitrarily from outside the class; mutations go through named methods, making the call sites explicit.
